## 0. Verified facts (I ran the formula, it checks out)

- Baseline (no actions): **52.56** ✓ matches doc
- Doc example (M7 Нура, M8 Нура, M10 Нура, M12, M5 Сарыарка), cost 95: **56.54** ✓ matches "≈56.5"
- Cheapest valid set (M9, M11, M10, M12, M4, all Нура), cost 61: **55.67**
- Search space is tiny: **694,395 valid plans**. Brute force in pure Python = 24s. With a precomputed cache JSON committed to repo = 0s at runtime.
- **Global optimum = 57.24** (M2 city, M3 Нура, M8 Нура, M9 Нура, M14 city, cost 98).
- Top 5 plans ALL dump every district-measure into Нура. The 0.3×min(D) term + N_crit penalty makes Нура the only district that matters. The whole game's ceiling is +4.68 over baseline.
- Trap: M11 in Алматы pushes T1 from 40 → 38.25 → triggers a −1 critical penalty. Good thing for the AI to catch.

These are your unit tests. If your engine doesn't produce exactly 52.56 / 56.54 / 55.67 / 57.24, the engine is wrong, not the doc.

## 1. The angle (what makes this not the 400th "calculator + chatbot")

Name suggestion: **«Кабинет акима»** (or whatever, pick in 30 seconds, don't bikeshed).

Pitch line: *"Everyone built a calculator with a chat window. We built a decision cockpit that already knows every one of the 694,395 legal plans, tells the akim exactly how many points he left on the table and why, and then hits him with a heating-main burst in Q3."*

Three things the judges will remember:

1. **Regret meter.** After the user submits 5 decisions: "Ваш Score 56.54. Максимально достижимый при этих правилах: 57.24. Вы на месте 1 203 из 694 395 (топ 0.2%)." Plus a Pareto chart (cost → best score) with the user's dot on it. Nobody else will do this because they assume the space is big.
2. **Agentic analyst that cannot lie about numbers.** The LLM is an agent with tools (`score`, `validate`, `optimize`, `what_if`, `remove_one`). Every number in its text is checked against tool output by a regex guard; a number that didn't come from the engine gets the response regenerated. This is the "LLM explains, does not count" requirement taken literally, and it's a concrete technical talking point.
3. **Q3 crisis ("5th hour").** After the plan is locked, a seeded random event hits (heating main burst in Алматы: C1 −12; smog winter in Сарыарка: E2 −10; school overcrowding in Есиль: S1 −8). The user must swap exactly one measure inside the same 100 budget. Score recomputed, AI explains what the crisis cost and whether the swap was right. Hits the optional criterion almost nobody will touch.

Everything else (timeline chart, leaderboard, auto-brief) is supporting cast.

## 2. Stack (optimised for the 25-point README/reproducibility criterion)

- **Engine**: pure Python, zero deps, `engine/` package. Dataset + measures live in `data/dataset.json` (not hardcoded in logic).
- **API**: FastAPI + uvicorn. SQLite for leaderboard.
- **Frontend**: ONE static `web/index.html` with Tailwind CDN + Chart.js CDN + vanilla JS. **No build step.** Served by FastAPI. `git clone` → `pip install -r requirements.txt` → `uvicorn api.main:app` → open localhost. That is the whole launch procedure. Judges will actually be able to run it.
- **LLM**: OpenAI API (tool calling) via `OPENAI_API_KEY`. Use a cheap fast model (gpt-5-mini class) — judges' patience > eloquence. Provider abstraction via `LLM_PROVIDER=openai|nvidia` so NVIDIA NIM (`NVIDIA_API_KEY`, OpenAI-compatible endpoint) is a one-line fallback. Spend credits here, not on pride.
- **Offline mode** (`LLM_PROVIDER=offline` or no key): template-based narrative from engine output. The app must fully work without any API key. This is not optional — a judge with no key gives you 0 on the "main scenario" otherwise.
- **Optimizer cache**: `data/optimizer_cache.json` (top-N plans, Pareto frontier by cost, score histogram for percentile). Committed. Generated by `python -m engine.optimize` (documented, reproducible).
- Docker: `docker compose up` as a bonus only if it takes <10 min. Not required.

## 4. API contract (agree in the first 15 minutes, then work in parallel)

Plan format everywhere: `{"decisions":[{"measure":"M7","district":"Нура"}, {"measure":"M12","district":null}, ...]}` — exactly 5.

- `GET /api/dataset` → districts, measures, rules (frontend renders from this, never hardcodes)
- `POST /api/validate` {plan} → `{valid: bool, reason: str|null, cost: int, remaining: int}` — frontend calls this on every change for live budget bar + red errors
- `POST /api/score` {plan} → 
  ```
  {score, baseline:52.56, delta, cost,
   districts:{Нура:{before:[10], after:[10], D_before, D_after}, ...},
   n_crit, crit_cells:[{district,indicator,value}],
   contributions:[{measure, district, cost, score_without, marginal}],   // remove-one
   timeline:[{q:0..8, score}],                                           // linear ramp after lag
   synergies_triggered:[...]}
  ```
- `POST /api/optimize` {plan} → `{best:{plan,score,cost}, rank, total_valid:694395, percentile, pareto:[{cost,score,plan}], best_at_same_cost}`
- `POST /api/analyze` {plan, lang:"ru"} → 
  ```
  {summary, strengths[], risks[], consequences[], tradeoffs[],
   recommendation:{plan, expected_score, why}, provider:"openai|offline", grounded:true}
  ```
- `POST /api/shock` {plan, seed} → `{event:{id,title,district,effects}, new_baseline_score, must:"swap_one"}`
- `POST /api/shock/resolve` {plan, event_id, swap:{out, in}} → same shape as /score + `{crisis_cost, recovered}`
- `POST /api/submit` {team, plan, score} ; `GET /api/leaderboard` → sorted list
- `GET /api/brief` {plan} → markdown one-pager (auto presentation, optional criterion)

## 5. Engine spec (Person A, first 45 min, Claude Code)

Formula exactly as in the doc:
1. `I' = clip(I + Σ effect × (8−L)/8 + synergy, 0, 100)`. City measures apply to all 5 districts. Synergy bonus is fixed (not lag-scaled), applied in the district of the FIRST measure in the pair (M1+M2 → district of M1; M10+M12 → district of M10; M5+M6 → district of M5).
2. `D_d = Σ w_k I'_dk`, weights T1 .10 T2 .10 E1 .09 E2 .11 S1 .11 S2 .11 B1 .09 B2 .09 C1 .10 C2 .10.
3. `D_avg = Σ pop_d D_d`.
4. `Score = 0.7 D_avg + 0.3 min(D_d) − N_crit`, N_crit = count of cells strictly < 40 after effects.

Validation, in this order, return first failure: exactly 5 · no duplicate measure · cost ≤ 100 · district-type has district / city-type has none · ≤2 per direction · M1×M3 anywhere · M4×M7 same district · M5×M13 same district.

Timeline: effect fraction at quarter q = `max(0, q − L)/8` (equals (8−L)/8 at q=8, consistent with the doc). Synergy: apply when both measures are active (q > max(L_a, L_b)). Say in README this is our interpretation of the lag.

Remove-one contributions: for each of the 5 decisions, score the plan with that decision removed (4-decision plan — bypass the "exactly 5" rule internally for this calc only) → `marginal = score − score_without`. Gives "worst value per cost" callout.

Optimizer: enumerate `combinations(options, 5)` where options = 10 district-measures × 5 districts + 4 city measures = 54. Prune by validate. Store top 200 plans, Pareto frontier, and a sorted score array (or histogram) for rank/percentile. 24s single-threaded; fine as a one-time script.

## 6. Agent spec (Person A, hour 2)

System prompt (RU): You are the chief analyst of the Astana akimat. You NEVER compute or invent numbers. All numbers must come from tool results. Structure output as JSON with the fields in `/api/analyze`. Explain trade-offs in terms a mayor understands: who benefits, which district is left behind, what the lag means (M3/M13 only 50% realised in 8 quarters), which critical cells (<40) remain.

Tools exposed to the model: `score(plan)`, `validate(plan)`, `optimize_same_budget(plan)`, `what_if(plan, swap)`, `remove_one(plan)`. Loop max 6 tool calls, then final JSON.

Number guard: extract all numbers from the final text; every number with a decimal or ≥ 10 must appear in the union of tool outputs (rounded to 1 dp) or in the dataset. If not → regenerate once with a "you invented N" message; if it fails again → fall back to offline template and mark `grounded:false`. Log it. Mention this in README under "Anti-hallucination".

Offline template: fills the same JSON from engine output (strengths = top 2 marginal measures; risks = remaining crit cells + lag-heavy measures; recommendation = best_at_same_cost from cache).

## 12. THE WOW LAYER (added after review — this is the story, everything above is the floor)

Honest answer to "what stops someone doing the same": nothing, technically. 2,500 people, same dataset, same formula. The moat is not a feature, it's a *finding* plus a *story* plus a *demo that the judges are inside of*. Here it is.

### The finding
The formula's optimum (57.24) puts every district-measure into Нура. Нура is 16% of the population. Есиль + Алматы (51% of the city) get nothing but city-wide crumbs. **The mathematically perfect akim gets fired.** That tension (Quality-of-Life Score vs. political survival) is the whole pitch, and it's true in the judges' own data.

### Four features that turn the finding into a show

**A. Approval Rating (political-risk layer, deterministic, engine/approval.py).**
Second gauge next to the AQLS: «Рейтинг акима». Per district: `approval_d = clip(45 + 10·ΔD_d + (6 if a district-measure landed in d else −8) − 3·crit_cells_d, 0, 100)`, city = Σ pop_d·approval_d, re-election line at 50. Calibrate the constants so the 57.24 optimum lands BELOW 50 and the doc example lands above. Clearly labelled "not part of AQLS; risk layer". AQLS stays THE score (compliance). This is where "strengths, risks, consequences" gets teeth.

**B. Совет районов (District Council).** On the Verdict screen, five deputies (one per district, persona from the district profiles: Есиль rich and stuck on bridges, Нура the outsider) each give a one-line reaction to the plan, quoting their district's real delta. One LLM call returns all five; offline mode uses templates. Demo moment: the Нура deputy is thrilled, the Есиль deputy asks why 27% of the city got nothing.

**C. «Астана Times, IV квартал 2028» (the consequence front page).** After the plan (and crisis) resolves, generate a newspaper front page: 4–5 headlines from the biggest deltas and the biggest unresolved problems ("В Нуре отменили вторую смену", "Мосты Есиля: пробки остались"), one editorial paragraph, a "critical cells" sidebar in red. Rendered as an actual newspaper-styled HTML block (serif, columns, masthead). Same LLM call as the council (one `/api/narrative` call → `{council:[5], newspaper:{headlines[], editorial}}`). This is the screenshot that goes on the README hero and on the last slide. Judges remember pictures, not JSON.

**D. Live play via QR (presentation weapon).** The optional "compare across teams" criterion becomes audience participation: expose the app via ngrok, put a QR on slide 1, judges play on their phones during the pitch, the live leaderboard is on the projector. Then you reveal the machine's optimum and show it loses on approval. Fallback if wifi dies: a 40-second screen recording made beforehand.

Plus what was already there: regret meter (rank among 694,395, ceiling, Pareto), Q3 crisis with forced swap, agent with number guard, offline mode.
