# Frontend decisions

One line per choice made without asking. Newest at the bottom.

1. **The first version was built before PLAN.md and `api/CONTRACT.md` were reachable.** That version is replaced. The page now follows `api/CONTRACT.md` exactly: plan format `{decisions:[{measure, district}]}`, district names as keys, and 10 indicators T1…C2.
2. **One place to configure.** `CONFIG` at the top of the script in `index.html`. The API base defaults to the same origin, because FastAPI serves `web/` at `/`. `?api=` overrides it.
3. **Mock mode, `?mock=1`, replays real API responses.** They were captured by `web/tools/capture_fixtures.py` for the doc example and stored in `web/mock/*.json`. Validation still runs client-side with the engine's rules. Any valid plan then shows the doc example's verdict, which is enough for development and screenshots.
4. **Automatic fallback.** If `GET /api/dataset` fails on load, the page switches to the recorded answers and shows an amber banner. That keeps the page usable if the backend is down on stage. Once the real API is in use, a failed call shows an error card with a retry button instead.
5. **The verdict needs four calls in parallel:** `/api/score`, `/api/optimize`, `/api/analyze`, and `/api/narrative`. Each panel has its own loading and error state, so a slow LLM never blocks Score, the approval gauge, or the regret meter. LLM calls get a 120 s timeout. Engine calls get 15 s.
6. **Live validation in the cabinet.** The page calls `/api/validate` on every change. It also runs a local copy of the rules with the "exactly 5" rule skipped, so conflicts show up while the plan is still partial. Cards and district choices that would break a rule are disabled, and the reason is shown.
7. **The district picker previews results.** For each district it shows the affected indicators today and at IV кв. 2028, with the lag share applied. It also shows population share, profile, and D. Cells below 40 are red.
8. **The approval gauge carries the contract's required label:** «слой политического риска, не входит в Score».
9. **Regret meter wording.** «максимум 57,24, ваше место N из 694 395, топ X%», where X is rank ÷ total_valid. The Pareto chart also marks the optimum, drawn red because it gets fired, and `balanced`, drawn amber. «Лучший план с рейтингом ≥50%» loads the balanced plan into the cabinet.
10. **Crisis flow.** It calls `/api/shock` with `seed` from `?seed=`, or a random one. The seed only picks among 3 events. The event card shows the no-swap damage from `score_before` and `new_baseline_score`, plus the staff hint in a collapsed section. `best_swaps` stays hidden so the player's choice is honest.
11. **The crisis comment is built from engine fields,** not from an LLM: `crisis_cost`, `recovered`, `swap_was_optimal`, `best_possible_swap`, and approval. It is labelled «числа из движка». The newspaper is re-requested with `event_id` and `swap`, so it covers the crisis.
12. **After the crisis,** the verdict shows the post-swap score with baseline 51.40 and labels it as the crisis baseline. The regret meter and AI panel keep the original plan's numbers and say so, because optimizer ranks are defined only without a crisis.
13. **Newspaper layout.** `headlines[0]` becomes the front-page headline, and the rest go into columns. The front page adds engine-derived blocks: «Что утвердил аким», a district D table, and «Цифры срока». When `crit_sidebar` is empty, the red sidebar names the weakest district.
14. **Leaderboard rooms without a backend change.** `?session=room` appends ` [room]` to the team name on submit and filters rows by that suffix. Rows without a suffix form the main hall. Asked in `API_REQUESTS.md` for a real `session` field.
15. **The «Показать оптимум машины» button pins two reference rows:** the optimum at 57,24 with 48,4%, marked Уволен, and the balanced plan at 57,00 with 53,4%, marked Переизбран. This is the leaderboard reveal from the pitch.
16. **The smoke test never writes to the real leaderboard by default.** It submits only in mock mode or with `SUBMIT=1`.
